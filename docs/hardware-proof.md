# Как доказано, что плата = Lemokey P1 Pro

Все проверки — по трём файлам:

* `stock/qmk_bin_ansi/ANSI_MKey PRO_260831.bin` — официальная прошивка MONTECH (67 928 байт),
  скачана с montechpc.com (download id 759203, внутри zip).
* `mkey/Mkey-Pro-Plus.bin` — сборка автора репозитория caloutw (77 100 байт).
* `.build/montech_mkey_pro_75_via.bin` — наша сборка из восстановленного исходника (67 276 байт).

---

## 1. Вектор-таблица и MCU

Первые 8 байт официального образа:

```
00 04 00 20   B9 01 00 08
```

* SP = `0x20000400`, reset = `0x080001B9` (Thumb) → ARM Cortex-M, флеш с `0x08000000`.
* Ровно то же самое в прошивке caloutw.
* В `info.json` Keychron для P1 Pro: `"processor": "WB32F3G71"`, `"bootloader": "wb32-dfu"` —
  Westberry WB32F3G71, Cortex-M4.

Неиспользуемые вектора указывают на `0x080001BB` (`b .` — вечный цикл), это штатный
паттерн QMK/ChibiOS.

## 2. Таблица LED-драйвера — главное доказательство

`g_snled27351_leds` — константный массив: на каждый из 81 светодиода 4 байта
(номер драйвера, канал R, канал G, канал B). От компилятора не зависит вообще.

Сигнатура первых шести записей:

```
00 0E 2E 1E  00 0D 2D 1D  00 0C 2C 1C  00 0B 2B 1B  00 0A 2A 1A  00 09 29 19
```

Найдена:

| Файл | Смещение |
|---|---|
| Официальная MONTECH | `0x0F5CC` |
| caloutw | `0x10A4C` |
| Наша сборка | `0x0F3A4` |

Побайтовое сравнение 324 байт нашей сборки и официальной: **0 расхождений**.
То есть распайка подсветки (2 драйвера, 81 LED, порядок каналов, переход
`A→G→D` и `0x0E→0x6E→0x8E`) идентична.

Дополнительно проверено: после 14 записей канала `A` идёт группа с кодами
`0x6E/0x8E/0x7E` — то есть `G_15 = 0x6E`, `I_15 = 0x8E`, `H_15 = 0x7E`;
ровно как в `snled27351.h` Keychron.

## 3. Раскладка

Сравнение официального VIA-JSON (`montech_via_json_ansi.json`) с
`keyboards/lemokey/p1_pro/via_json/p1_pro_ansi_encoder_v1.0.json`:
6 строк × 15 колонок, отображение matrix → physical совпадает полностью.
Отличия — только косметика JSON (лишняя пустая строка в массиве и пробелы в `"5, 9"`).

Строка 3: пропущена позиция `[3,12]`; строка 4: пропущены `[4,1]`, `[4,14]`;
строка 5: пропущены `[5,3]`, `[5,4]`, `[5,5]`, `[5,7]`, `[5,8]` — совпадает в обоих файлах.
Такое совпадение «дырок» в матрице случайным быть не может.

## 4. USB-дескрипторы

В официальном образе два места с `VID 0x362D / PID 0x1700` (смещения `0x034D4` и `0x0FD8D`).

Строки:

| Что | Официальная | caloutw | Наша |
|---|---|---|---|
| product (UTF-16) | `MKey PRO 75` | `MKey PRO 75` | `MKey PRO 75` |
| product (ASCII) | `0x0F33B` | `0x109E3` | есть |
| manufacturer (UTF-16) | `Keychron` | `Keychron` | `MONTECH` |

Вывод: вендор собрал прошивку из кода Keychron и не поменял даже строку производителя.
PID `0x1700` совпадает с официальным VIA-JSON (`"productId": "0x1700"`).

## 5. Кеймап вытащен из официального бинарника

Массив `keymaps[][6][15]` лежит в `.rodata`. Для нашей сборки адрес известен из ELF
(`keymaps` = `0x0800f4fc`, размер `0x2d0` = 720 байт = 4 слоя × 90 × 2). В официальном
образе он найден по сигнатуре `29 00 3A 00 3B 00 3C 00` (Esc, F1, F2, F3) на `0x0F8AC`.

Декодированный слой 0 официальной прошивки:

```
r0: ESC  F1  F2  F3  F4  F5  F6  F7  F8  F9  F10 F11 F12 DEL  <custom 0x7E13>
r1: GRV  1   2   3   4   5   6   7   8   9   0   -   =   BSPC HOME
r2: TAB  Q   W   E   R   T   Y   U   I   O   P   [   ]   \   PGUP
r3: CAPS A   S   D   F   G   H   J   K   L   ;   '       ENT PGDN
r4: LSFT     Z   X   C   V   B   N   M   ,   .   /   RSFT UP
r5: LCTL LGUI LALT          SPC             RALT MO3 RCTL LEFT DOWN RGHT
```

Это ровно тот же скелет, что у P1 Pro; `MO3` в позиции `[5,10]` — клавиша Fn,
`0x7E13` на энкодере — вендорский «Btn mode change» (смена режима энкодера,
его нет в публичном коде Keychron — реализуем сами, если нужно).

Слой 1 официальной прошивки (функциональный) содержит: `RGB_TOG`, `RGB_MOD`, `RGB_SPI/SPD`,
`0x7E14` («выключить подсветку кнопки»), медиа `prev/play/next`, `PSCR`, `MUTE`,
`0x7E06` (Task View), `0x00B2` (Sleep), `0x7E12` («Boss»), `BT_HST1..3`, `2.4G`,
`INS`/`END` на Fn+PgUp/PgDn (совпадает с changelog официальной прошивки),
и RGB-регулировки на стрелках.

## 6. Откуда берётся строка даты сборки

В обеих прошивках есть строка вида `2026-09-09-10:37:12`:

* официальная — `0x0F320`, `2026-09-09-10:37:12`;
* caloutw — `2026-04-02-09:43:29`;
* наша — `0x0F0FD`, `2026-11-19-01:12:30`.

Формат задаётся в `lib/python/qmk/cli/generate/version_h.py`:

```python
TIME_FMT = '%Y-%m-%d-%H:%M:%S'
```

То есть все три собраны штатной системой сборки QMK без «вырезания» служебных строк.

## 7. Почему побайтовый diff бесполезен

Сравнение «наше vs официальная» по одинаковым смещениям даёт ~6.5% совпадения байт —
и это нормально: другой GCC генерирует другой код по всему файлу. Поэтому сравнение
ведётся по:

1. константным таблицам (LED, геометрия, дескрипторы) — они от компилятора не зависят;
2. размеру образа — 67 276 против 67 928 байт (разница ~0.9%);
3. структуре: те же 6×15, те же пины в `info.json`, тот же драйвер.

Итоговая уверенность: **железо идентично, прошивка эквивалентна**.

## 8. Порядок пинов матрицы

Первая версия порта взяла `matrix_pins` от P1 Pro целиком — и это была ошибка:
на клавиатуре каждая клавиша печатала «чужую», стабильно и без пропусков.
Такой симптом означает, что сканирование работает, но **индексы строк/столбцов
не совпадают с физической разводкой**, то есть переставлен порядок пинов.

В QMK массивы пинов лежат в `.rodata` как обычные `pin_t` (32-битные адреса вида
`0x4000_0000 | порт | пад`, где A = `0x0000`, B = `0x0400`, C = `0x0800`,
D = `0x0C00`). В нашей сборке адреса известны из ELF:
`matrix_init_pins` грузит 15 пинов из `0x0800F834`, затем 6 из `0x0800F870`.
Значит достаточно найти в официальном образе точно такой же массив из 21 значения —
и прочитать его **в порядке следования**.

| | Порядок пинов |
|---|---|
| P1 Pro (`matrix_pins.cols`) | `C14 C15 C2 C3 A0 A1 A2 A3 B10 B12 B13 C7 C8 C9 A10` |
| Официальная MKey PRO 75 | `A10 C9 C8 C7 B13 B12 A3 B10 C14 C15 C2 C3 A0 A1 A2` |
| Строки (обе) | `C12 D2 B3 B4 B5 B6` |

Набор пинов одинаковый (15 столбцов и 6 строк), различается только порядок столбцов —
поэтому и получалась «перестановка внутри строк», а не мёртвые клавиши.

Смещения массивов в образах:

| Образ | Массив пинов |
|---|---|
| Официальная | `0x0FA80` (и копия `0x1019C`) |
| Наша, после правки | `0x0F834` (и копия `0x0FF4C`) |

После правки 21 значение совпадает байт в байт.

Дополнительные проверки того же рода:

* `DRIVER_CS_PINS` `{ B15, C6 }` — найдены в официальном образе (`0x10398`) в том же порядке;
* пины энкодера `{ A8, A9 }` — найдены (`0x00A98`) в том же порядке;
* полный набор GPIO, которые вообще упоминает прошивка, — **27 из 27**, расхождений нет
  (то есть SPI, I2C, беспроводной модуль и батарея используют те же ноги).

Побочный эффект исправления: `bootmagic` снова висит на реальной клавише Esc
(до правки он срабатывал с другой физической клавиши, потому что позиция `[0,0]`
указывала не туда).

## 9. Кольцо энкодера, фаза и ток драйвера

У P1 Pro подсветка — 81 LED, у MKey PRO 75 их **88**: последние 7 — кольцо вокруг ручки.
В официальной прошивке после 81-й записи `g_snled27351_leds` идут ровно 7 записей:

```
00 3F 5F 4F   00 6F 8F 7F   01 0F 2F 1F   00 9F BF AF
01 6F 8F 7F   01 3F 5F 4F   00 0F 2F 1F
```

Семь штук — совпадает с семью секциями «кольца» в VIA-меню caloutw (Top, Upper Right,
Lower Right, Bottom, Lower Left, Left, Upper Left). В нашей сборке эти 7 записей
добавлены, таблица целиком (352 байта) сверена и даёт **0 расхождений**.

Важная деталь: кольцо висит на каналах с индексом `_16`, в том числе на группах
**J/K/L** (`0x9F`, `0xBF`, `0xAF`). Группы J/K/L существуют только при 12 фазах
сканирования. Проверка по машинному коду инициализации драйвера:

```
наша (было):   ... 03 23 (movs r3,#3)  14 22 (reg 0x14 = SCAN_PHASE)   -> 9 фаз
заводская:     ... 00 23 (movs r3,#0)  14 22                          -> 12 фаз
```

То есть при 9 фазах кольцо физически не могло гореть. Исправлено на
`MSKPHASE_12CHANNEL`; после правки участок инициализации совпал с заводским **байт в байт**.

Ток драйвера (`SNLED27351_CURRENT_TUNE`, 12 регистров 0x18..0x23) у P1 Pro — `0x2C`,
у MKey — `0x1B`. Наша сборка грузит таблицу по тому же указателю, что и заводская
(литерал `0x0800F367`), значения сверены: `1B 1B ... 1B` (12 байт).

## 10. Индикация батареи — почему «не работает» по кабелю

В общем коде (он же в заводской прошивке) показ уровня заряда намеренно ограничен
беспроводным режимом:

```c
case BAT_LVL:
    if ((get_transport() & TRANSPORT_WIRELESS) && !usb_power_connected()) {
        bat_level_animiation_start(battery_get_percentage());
    }
```

Плюс сам рендер индикаторов (`LED_INDICATORS_KB`) выполняется только при
`get_transport() & TRANSPORT_WIRELESS`. Напряжение батареи приходит от модуля LKBT51
(`battery_measure()` → `lkbt51_read_state_reg(0x05, 0x02)`), а не с локального ADC.
Поэтому по кабелю нажатие `Fn+B` не показывает ничего — и в заводской прошивке тоже.
Проверять нужно беспроводно (2.4G/BT, кабель выдернут).
